## 组队要求

1. **方向一**：每队 **4-5 人**；**方向二**：每队 **4 人**。
2. **不允许跨方向组队**。一支队伍只能报名一个方向，队内所有人按同一方向的题目完成考核。
3. 组队完成后请自行确认队内分工。我们看重每位成员的团队合作。
4. 每人只能出现在一支队伍中，不得重复报名或中途更换队伍。

## 提交方式

1. 提交**团队的 Git 仓库链接**（项目源代码所在的仓库，而非打包文件）。
2. 截止时间：**2026 年 12 月 6 日（周日）24:00**，逾期视为放弃。以仓库主分支上的内容为准，截止后不再接受补交或修改。
3. 提交入口（问卷 / 表单 / 群接龙等）将在群公告中发布，请留意群消息，按公告要求填写队伍信息与仓库地址。

## 仓库要求⭐⭐

我们会直接克隆你的仓库并尝试运行，仓库本身就是评分的一部分。请把它当成一个**要交给别人接手**的项目来做：

- 使用 **Git** 做版本控制，源代码托管在 GitHub，仓库设为 **public**，提交内容放在 `main` / `master` 分支。
- **分多次提交，而不是最后一次性上传**。每次完成一部分功能就 commit 一次，commit message 说清楚这次改了什么（可参考 [Angular 提交规范](https://zj-git-guide.readthedocs.io/zh-cn/latest/message/%E5%BC%95%E8%A8%80/) 或 [gitmoji](https://hooj0.github.io/git-emoji-guide/)）。
- **不要提交 IDE 配置、`.idea`、`.vscode`、虚拟环境、缓存、模型权重、数据集等无关或体积巨大的文件**。
- 仓库根目录必须有 **README.md**（Markdown 书写），至少覆盖：
  - 项目简介：做了什么、解决什么问题、用了什么技术栈；
  - 目录结构说明；
  - 环境搭建与依赖安装步骤（写清版本）；
  - 运行 / 训练 / 测试命令，能照着跑起来；
  - 已验证的功能清单，以及已知的问题与未完成部分。
- 文档、报告统一用 **Markdown** 提交，图片放进仓库内的 `assets/` 等目录并确认**在网页上能正常显示**，不要出现指向本地路径的图片。
- 代码结构清晰，按功能分模块，变量与函数命名可读，关键逻辑有注释，不要把所有东西塞进一个文件。
- 提交前确保我们可以复现

## 评定说明

本轮考核不设公开的分数细则，最终结果由评审综合判断，主要从以下几个维度衡量：

- **功能完整度与可验证性**：题目要求的必做内容是否真的做出来、能不能实际操作验证，而不是只有文档描述；
- **工程规范**：项目结构、依赖管理、代码组织与可读性，是否有基本的测试或自检手段；
- **文档规范**：README 与相关文档是否完整、准确，能否指引用户跑起来；
- **仓库规范**：提交历史、分支使用、`.gitignore`、仓库整洁度，能否看出真实的开发过程；
- **团队合作**：分工是否合理、是否真正协作完成，答辩时能否说清各自负责的部分与整体设计；
- **完成度与取舍**：在给定时间内做到什么程度，没做完的部分是否说明清楚、是否有合理的降级方案。

各方向的题目文档中会补充该方向额外关注的点，请一并阅读。

## 注意事项

1. **先读完所有要求再开始写代码**，尤其是提交格式与仓库要求，不要等到最后才发现要返工。
2. 允许使用 AIGC 工具辅助开发，这在当下是常态；但请确保你对自己提交的代码与方案有足够的理解，答辩与路演环节会就实现细节、设计取舍提问，答不上来会影响评定。
3. 允许参考公开资料与开源项目，但**核心实现请自己完成**，直接套用他人项目或购买成品提交的，一经发现按无效处理。
4. 时间紧张时不要慌，把已经完成的部分及时提交上来，并在文档里说明清楚做到哪一步、还剩什么，好过最后交一个跑不起来的仓库。
5. 遇到题目描述不清的地方，可以在群里提问，以群内答复为准。

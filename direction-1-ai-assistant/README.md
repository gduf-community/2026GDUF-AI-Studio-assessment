# 方向一 · 智能应用考核说明

## 考核背景

以 LLM 为代表的生成式模型，已经把「做一个能对话的应用」的门槛压得很低。调用一次 API、拼一段提示词，就能拿到看起来像样的回答。但把这样的原型变成一个人愿意每天打开、数据不会丢、换台机器也能跑起来的应用，是另一回事。

真实的智能应用通常要处理这几类问题：

- 用户的输入是自然语言、图片、截图，格式不统一，信息经常缺失
- 模型输出不稳定，同样的输入可能给出不同的结构，需要约束与校验
- 业务数据要落到数据库里，分类、统计、查询不能只靠一次对话
- 模型能力之外还有工程：配置管理、异常处理、依赖版本、部署方式

本轮考核基于这一背景：

> **从两个候选题材中选择一个，做出一个可运行、可复现的 AI 应用。**

请注意：

- 本考核 **不要求训练模型**，重点是应用层的设计与实现
- 评分不只看功能多少，也看工程规范、文档质量与团队协作

## 考核目标

通过本次考核，我们主要关注以下能力：

- 把模糊的需求收敛成可实现的功能清单
- 对 LLM / OCR / RAG 等能力的实际调用与效果调优
- 自然语言输入到结构化数据的转换与持久化
- 应用工程的结构设计、依赖管理与部署
- 使用 Git 进行协作开发与版本管理

## 选题 A：个人记账与消费分析 AI 助手

### 背景与定位

个人记账长期是个「知道有用但坚持不下来」的场景。传统记账软件要求用户逐笔选择分类、填写金额，一笔消费要五六次点击，几周之后就没人再打开。而用户真正想知道的往往不是流水本身，是「这个月吃饭花了多少」「哪里超支了」这类问题。

大模型与 OCR 的成熟，让另一种交互方式变得可行：用户直接说「昨天打车 32 块」，或者拍一张小票照片，系统自己完成金额提取、分类、入库；查账时也用一句话问，而不是在筛选器里点半天。

本题参考 FinTechathon「银行 AI 智能体」的思路，但把场景从对公业务下沉到个人财务：数据规模小、可以自己造、不涉及真实资金。难点不在模型本身，在于把语音/文本/图片三种输入收敛成一套可靠的数据结构，并让后续的统计与查询建立在真实入库的数据之上。


### 必须完成的最小功能集（MVP）

以下四项 **至少打通 3 项**，未达到视为未完成基本要求。

1. **自然语言记账 + 小票 / 截图 OCR 录入**
   - 支持一句话记账，例如「午饭 25，和同事 AA」
   - 支持上传小票或支付截图，识别出金额、商户、时间
   - 识别结果允许用户确认或修正后再入库
2. **消费自动分类与统计**
   - 对每笔消费给出类别（餐饮、交通、购物等），类别体系自行设计
   - 按类别、按时间维度统计，结果可查询
3. **自然语言查账**
   - 例如「我上个月吃饭花了多少？」「这个月哪类花得最多？」
   - 需要真正解析时间范围与类别，而不是把问题原样丢给模型自由回答
4. **预算设定与超支提醒**
   - 可为类别或总额设定月度预算
   - 接近或超出预算时给出提醒

### 可选功能（加分项）

根据时间与能力自行选择，不要求全部实现：

- 理性消费与理财方向的轻量建议，例如月度对比、异常支出提示
- 多轮追问与澄清：信息不全时主动反问，而不是猜一个数
- 可视化报表：分类占比、月度趋势
- 对诱导性、越界请求的拒绝边界，例如用户要求「帮忙找贷款口子」「绕过额度限制」时的回应方式

以上只是方向性的举例，不必照单实现。本轮参与考核的队伍较多，必做清单能拉开的差距有限，可以按照自己的想法继续完善。

### 技术基线

大模型 API + OCR / 视觉模型 API + 结构化存储（如 SQLite）+ 简单图表。自己准备一份示例账单 CSV，先把端到端链路跑通。

## 选题 B：学习辅导 AI 助教（限定学科自选）

### 背景与定位

用大模型答疑已经不是新鲜事，但直接拿通用对话模型当助教，效果往往停留在「这道题答案是什么」。真正的学习过程需要重复：讲懂一个知识点、记下做错的题、针对薄弱环节再练一遍、看到自己的进度。

本题要求针对 **某一门课或一个学科** 做这样一个闭环，而不是做一个什么都能问的通用助手。限定学科是刻意的约束：只有把范围收窄，才可能把知识点组织起来、把错题归类做得合理、让生成的练习真正落在薄弱点上。

学科自选，例如高数、线代、英语、C 语言、数据结构等，选定后只做这一门。


### 必须完成的最小功能集（MVP）

以下四项 **至少打通 3 项**，未达到视为未完成基本要求。

1. **知识点问答**
   - 能解释概念、能举例，回答限定在选定学科范围内
2. **错题录入与自动归类**
   - 支持录入题目、答案、错误原因
   - 能按知识点或题型自动归类
3. **根据薄弱点生成针对性练习**
   - 依据错题分布生成练习，而不是随机出题
   - 生成的题目应可作答、可判定对错
4. **学习进度 / 掌握度记录**
   - 记录练习与错题情况，能看出哪些知识点掌握得差

### 可选功能（加分项）

根据时间与能力自行选择，不要求全部实现：

- 解题步骤可解释，给出推导过程而不只是最终答案
- 个性化薄弱点画像，例如按知识点给出掌握度估计
- 结合教材 / 课件做 RAG，并在回答中给出引用出处
- 练习结果的反向更新：做错的题回流到错题本

以上只是方向性的举例，不必照单实现。本轮参与考核的队伍较多，必做清单能拉开的差距有限，可以按照自己的想法继续完善。

### 技术基线

大模型 API + 一个题库（自建 JSON 或公开题库均可）+ 可选接入课件做 RAG。

## 技术与工程要求

### 1. 通用要求

- 应用需可交互使用，不接受只有设计文档或 PPT 的提交
- 允许使用任何大模型 / 视觉 / 语音 API 与开源组件，需在 README 中写清用了什么、如何配置
- 密钥通过环境变量或配置文件注入，**不得将真实 API Key 提交到仓库**
- 需要准备一份演示数据（示例账单、示例错题等），使评审无需自行构造数据即可跑通主流程
- 数据库、缓存等本地依赖的启动方式需在文档中写明

### 2. Docker 与复现

- 项目需提供 Dockerfile（或 docker-compose），能够通过容器启动完整服务
- README 中的启动命令必须与实际一致，评审会按文档从零执行一遍
- 容器内的数据持久化路径、端口、环境变量需说明清楚

### 3. 代码规范

- 使用 UTF-8 编码
- 命名符合所选语言的规范，避免无意义缩写与拼音命名
- 模块按功能划分，避免所有逻辑堆在单个文件
- 关键函数与接口需有说明，复杂逻辑需有注释

### 4. Git 与工程管理

- 必须使用 Git 进行版本控制，仓库为 **公开仓库**（GitHub / Gitee 等均可）
- 需要合理的 commit 粒度与规范的 commit message，避免最后一次性上传
- 不需要提交 IDE 配置、虚拟环境、模型缓存等与项目无关的文件

6. 若部署了在线可访问的 Demo，附上地址
7. 答辩演示 PPT（无具体模板要求）

## 评定说明

本轮考核不设公开的分数细则，最终结果由评审综合判断。除[根目录的通用维度](../README.md#评定说明)外，本方向主要关注：

- **功能完整度**：必做清单中实际打通了几项，完成的部分是否真实可用
- **AI 能力的使用**：模型、OCR、RAG 等能力是否用得合理，有没有针对场景做约束与调优
- **AI 工具的利用**：怎么用 AI 辅助编码、设计提示词与上下文、组合 OCR / RAG / 工具调用，遇到模型能力边界时怎么绕过去
- **可复现性**：评审能否按文档与 Docker 步骤，在自己的环境里把项目跑起来
- **工程与文档规范**：项目结构、依赖管理、README 与实际是否一致
- **团队合作**：分工是否清晰，答辩时能否讲清整体设计与各自负责的部分

## 注意事项

1. 先跑通再优化。端到端链路没打通之前，不必急着调模型效果。
2. API Key 不进仓库，提交前检查一遍提交历史。
3. 评审可能会现场试用，请确保根据文档可以复现，可以提前准备测试数据。
